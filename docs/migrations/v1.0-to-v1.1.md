# v1.0 → v1.1 迁移指南

v1.1 是 v1.0 之上的**新能力层**:Hooks 生命周期。把「每次工具调用前想检查」「每次调用
后想审计」「session 开始时想 git fetch」「每轮拿项目代码风格摘要」这类
**「事件 + 条件 + 动作」清晰的重复工作**,从手动盯变成机器自动做。
**无 breaking change** — 不写 `hooks:` 块的 v1.0 项目行为完全保留。

---

## 一、发生了什么变化

| 维度 | v1.0 | v1.1 |
|------|------|------|
| 工具调用前的精细策略 | 只能借 L3 规则(`Bash(git *)` 之类) | L1 → **hook.pre** → L2-L5 流水线;hook.pre 能基于参数条件精细拒 |
| 工具调用后的审计 | 自己写外层脚本 | `event: tool.post` 必触发(完整审计,不管谁拒) |
| 自定义注入到 LLM 上下文 | 改 Skill body / system prompt | `event: turn.start` + `action: prompt` + `slot: sticky_reminder` |
| 自定义 hard 行为(session/turn 起头做事) | 没有 | 11 个 lifecycle 事件:`session.start/end`、`turn.start/end`、`message.received/sent`、`tool.pre/post`、`system.error/compaction/cancel` |
| ToolResult 字段 | 5 字段(`tool_call_id/content/is_error/offloaded_to/original_size`) | +3 字段:`execution_status` / `denied_by` / `denied_hook_id`(`is_error` 派生) |
| 配置入口 | `config.yaml` 顶部 5 块(instr/memory/sessions/commands/skills) | + `hooks:` 块(嵌同一文件,启动顺序在 permissions 之后) |
| Permission pipeline 入口 | `permissions.check(call, ctx)` 一处 | + `permissions.check_layers_2_through_5(call, ctx)`(跳过 L1)+ `permissions.blacklist_check(call)`(仅 L1) |

## 二、Hook 配置格式

### 2.1 字段表

```yaml
hooks:
  - id: <unique>             # 必填,非空,文件内唯一
    event: <11 values>       # 必填,见 §3.1 事件清单
    if:                      # 可省,见 §2.3 条件语法
      all: [...]   或 any: [...]
    actions:                 # 必填,≥ 1 条
      - action: shell|http|prompt|sub-agent
        # 各 action 子字段见 §4
    async: true              # 可省;仅 `tool.post` 允许
    timeout_seconds: 30      # 可省,≥ 1, ≤ 300
    run_once: false          # 可省;true → 全 session 只跑一次
```

> **`if` 与 `async` 的 YAML key**:`if` 是 Python 保留字,schema 用 `alias="if"` 接;
> `async` 同理用 `alias="async"`。YAML 写法照常,反序列化后字段名带下划线后缀(`if_` / `async_`)。

### 2.2 完整示例

```yaml
hooks:
  # ① tool.pre:每次 Bash 调用前做权限二次检查
  - id: block-dangerous
    event: tool.pre
    if:
      all:
        - tool: "Bash"
        - arg.command:
            regex: 'rm\s+-[rR][fF]|chmod\s+777|sudo\s+'
    actions:
      - action: shell
        command: |
          echo "$(date -Iseconds) BLOCK tool.pre Bash $TOOL_CALL_ID
            command=$ARG_COMMAND
            reason=命中 rm -rf / sudo / chmod 777 正则" \
              >> .baozicode/audit.log
          exit 1   # 非 0 退出 → deny
        timeout_seconds: 5

  # ② turn.start:每轮注入项目代码风格提醒
  - id: inject-style
    event: turn.start
    actions:
      - action: prompt
        content: |
          本项目代码风格:PEP 8 + 100 字符行宽 + 类型注解必须 +
          pytest 单元测试 + 不引入新依赖除非经我确认。
        slot: sticky_reminder   # 默认;跨轮持久,直到 /clear

  # ③ tool.post (异步):后台审计 + 磁盘持久化
  - id: audit-bash-post
    event: tool.post
    async: true               # 后台跑,不阻塞下一轮
    if:
      all:
        - tool: "Bash"
    actions:
      - action: shell
        command: |
          echo "$(date -Iseconds) tool.post Bash exit=$ARG_RESULT exit_code=$?" \
            >> .baozicode/audit.log
          exit 0
        timeout_seconds: 5
        enqueue: false        # 默认:不灌入下一轮 LLM 上下文

  # ④ session.start:session 起来时自动 git fetch
  - id: session-bootstrap
    event: session.start
    run_once: true
    actions:
      - action: shell
        command: "git fetch --all --prune 2>&1"
        timeout_seconds: 30
```

### 2.3 条件(if)语法

| 形式 | 示例 | 含义 |
|---|---|---|
| **exact**(默认) | `tool: "Bash"` | 字符串相等 |
| **glob** | `arg.command: {glob: "ls *"}` | `fnmatch` 通配 |
| **regex** | `arg.command: {regex: "rm\\s+-rf"}` | `re.search` 命中 |
| **not_exact** | `arg.x: {not_exact: "/etc"}` | 反向精确 |
| **not_glob** | `arg.x: {not_glob: "**/.env"}` | 反向 glob |
| **not_regex** | `arg.x: {not_regex: "^/dev/"}` | 反向 regex |

YAML 写法两种等价:

```yaml
# 简写:
arg.command: {glob: "ls *"}
# 或展开:
arg.command:
  kind: glob
  value: "ls *"
```

逻辑组合(`all` / `any` 二选一,不能混):

```yaml
if:
  all:                          # 全部满足才命中
    - tool: "Bash"
    - arg.command: {regex: "rm\\s+-rf"}
# 或:
if:
  any:                          # 任一满足即命中
    - tool: "Bash"
    - tool: "Write"
```

**省略 `if`** 等价于 `if: {}`(无条件触发)。

## 三、事件流 + 流水线形态

### 3.1 11 个 lifecycle 事件

| 事件层 | 事件 | 触发时机 | 能否拦截 |
|---|---|---|---|
| **session** | `session.start` | `Agent.run()` 入口顶部 | 否(只注入 prompt) |
| | `session.end` | `Agent.run()` `finally` 块,任何路径都触发 | 否 |
| **turn** | `turn.start` | 每个 iteration 顶部,LLM stream 之前 | 否 |
| | `turn.end` | 每个 iteration 底部,工具执行后 | 否 |
| **message** | `message.received` | `conversation.add_user()` 之前 | 否 |
| | `message.sent` | `conversation.add_turn()` 之后 | 否 |
| **tool** | `tool.pre` | tool_call 实际执行前 | **是**(改 ToolResult) |
| | `tool.post` | 任何 tool_call 尝试之后(L1/hook.pre/L2-L5 拒 或 成功 / 失败) | 否(完整审计) |
| **system** | `system.error` | Agent 即将抛未处理异常时 | 否 |
| | `system.compaction` | v0.7 上下文压缩跑前(offload / 摘要前) | 否 |
| | `system.cancel` | `USER_CANCELLED` 触发时 | 否 |

### 3.2 Tool-call 流水线形态

```
Agent.tool_call(call)
│
├─①  L1 hard blacklist (v0.5, 硬墙不可绕过)
│    └─ deny → ToolResult(execution_status=block_l1, denied_by=l1_blacklist)
│
├─②  hook.pre (v1.1)         ⬅ 多 hook 串行短路,首个 deny 赢
│    └─ deny → ToolResult(execution_status=block_hook_pre, denied_by=hook_pre,
│                          denied_hook_id=<id>, content=reason)
│
├─③  L2 sandbox → L3 rules → L4 mode → L5 user modal (v0.5)
│    └─ deny → ToolResult(execution_status=block_permission, denied_by=l2_l5_permission)
│
├─④  execute_tool_call
│    ├─ success → ToolResult(execution_status=executed_success)
│    └─ error   → ToolResult(execution_status=executed_failed)
│
└─⑤  hook.post (v1.1, try/finally 包整个流水线) ⬅ 必触发,完整审计
```

### 3.3 启动顺序

```
1. config (AppConfig.load)
2. permissions              ← v0.5
3. hooks (NEW in v1.1)     ← HookRegistry.freeze() 校验 + create_dispatcher()
4. instructions             ← v0.8
5. memory                   ← v0.8
6. sessions                 ← v0.8
7. commands                 ← v0.9
8. skills                   ← v1.0
9. Agent(... hook_registry=registry.create_dispatcher())
```

`HookRegistry.freeze()` 跑期间任一字段错 → `SystemExit(1)`,启动阻塞。

## 四、4 种 Action 详解

### 4.1 总表

| Action | 拒绝判定 | 拒绝原因 | 必要字段 |
|---|---|---|---|
| `shell` | `exit_code ≠ 0` | stdout 第一行(空兜底 "hook shell 拦截高危工具调用") | `command` |
| `prompt` | **无拒绝能力**(只注入) | — | `content` |
| `http` | `parse_expr` 赋值 `res.deny = True` | `res.deny_reason` | `url` + `parse_expr` |
| `sub-agent` | `parse_expr` 赋值 `res.deny = True` | `res.deny_reason` | `goal` + `parse_expr`(v1.1 占位,子 Agent 实际跑通 v1.1.1) |

拒绝**判定** + action 类型解耦,沿用各自原生语义(shell exit_code / http parse_expr)。

> **shell action 不允许**显式 `deny` / `deny_reason` 字段(走 exit_code);**prompt
> 不允许**任何拒绝字段;**http / sub-agent 必须**配 `parse_expr` 才能有拦截能力。

### 4.2 shell

```yaml
- action: shell
  command: "echo blocked; exit 1"
  timeout_seconds: 30       # 默认 30,最大 300
  enqueue: false            # 默认:shell 输出不进 LLM 上下文
```

**Hook 可读环境变量**:

| 变量 | 内容 |
|---|---|
| `$TOOL_NAME` | 当前 tool 名(如 `Bash`) |
| `$TOOL_CALL_ID` | 当前 tool_call.id |
| `$EVENT` | 当前事件名(如 `tool.pre`) |
| `$HOOK_ID` | 当前 hook.id |
| `$ARG_<NAME>` | 当前 tool_call 的每个 argument(如 `Bash` 调用的 `command` → `$ARG_COMMAND`) |
| `$ARG_RESULT` | hook.post 时为 ToolResult.content;其他事件为空 |

### 4.3 prompt

```yaml
- action: prompt
  content: "..."                # 必填
  slot: sticky_reminder         # 默认;sticky_reminder | stable_system | temp
```

| Slot | 注入位置 | 持久性 | 校验 |
|---|---|---|---|
| `sticky_reminder`(默认) | `_inject_reminders` 拼到 `messages[-2]` | 跨轮持久,直到 `/clear` | — |
| `stable_system` | `BuiltPrompt.stable_system` 段,byte-identical | 显式 `clear_stable_system_overrides` 或重启清空 | 不允许 `event ∈ {tool.pre, tool.post}`(校验拒绝) |
| `temp` | 当轮 assistant 上下文 | 当前轮可见,下轮消失 | — |

> **v1.1.1 起**:`/clear` 同时清空 `Agent._pending_reminders`(sticky hook_prompt reminder)
> + `Agent._hook_stable_overrides`(`## Hook Overrides` 段)+ `Agent._temp_reminders` 三类运行时状态。
> 实现走 `baozicode.hooks.clear_hook_runtime_state(agent)` helper(chat_screen `_clear_conversation` 调它)。
> Hook 定义本身(`config.yaml: hooks:` 列表)不动,只清运行时注入。

### 4.4 http(sub-agent 形式相同)

```yaml
- action: http
  url: "https://risk-api.example/check"
  method: POST                 # GET(默认) | POST
  body:                        # 可选,JSON 字典,自动序列化为 body
    content: "$ARG_COMMAND"
  parse_expr: |
    res.deny = body.risk > 0.8
    res.deny_reason = body.label
  timeout_seconds: 30
```

**parse_expr 实现**:`simpleeval` 沙箱(无 exec、无 import、无 lambda、无函数调用)。
可读写:

| 标识符 | 类型 | 含义 |
|---|---|---|
| `res` | `SimpleNamespace` | 写 `res.deny` / `res.deny_reason` 决定拦截 |
| `body` | `dict` / `list` / `str` / `None` | 解析后的 HTTP response body |
| `status` | `int` | HTTP status code |
| `headers` | `dict[str, str]` | response headers |

> HTTP 4xx/5xx、连接异常**不**自动触发工具拦截(视为接口调用失败,不是主动拦截);
> 要拦截必须 parse_expr 内 `res.deny = True`。

### 4.5 sub-agent

```yaml
- action: sub-agent
  goal: "分析这段命令的风险等级"
  model: claude-sonnet-4-6     # 可省,默认走主后端
  parse_expr: |
    res.deny = res.output.risk_level == "high"
    res.deny_reason = res.output.reason
  timeout_seconds: 120
```

> v1.1 是**占位**:同进程内起子 agent 跑通 stub,完整独立 Runner 留作 v1.1.1。
> 即使 stub 失败也只是 hook fail-open,不阻断主流程。

## 五、ToolResult 新字段 + 派生关系

### 5.1 字段表

| 字段 | 类型 | 何时填 |
|---|---|---|
| `execution_status` | `Literal["block_l1", "block_hook_pre", "block_permission", "executed_success", "executed_failed"] \| None` | 每次 ToolResult 构造;老代码不填默认为 None(保留兼容) |
| `denied_by` | `Literal["l1_blacklist", "hook_pre", "l2_l5_permission"] \| None` | 仅 `execution_status ∈ block_*` 时填,否则 None |
| `denied_hook_id` | `str \| None` | 仅 `execution_status == block_hook_pre` 时填,记首个 deny 的 hook.id |

### 5.2 派生关系

```python
@dataclass
class ToolResult:
    ...
    def __post_init__(self):
        if self.execution_status is not None:
            # 派生 is_error,覆盖调用方显式传入值
            self.is_error = (self.execution_status != "executed_success")
```

**老调用方式完全兼容**:

```python
# v1.0 老代码:
r = ToolResult(tool_call_id="x", content="y", is_error=True)
#  → execution_status=None, is_error=True(走显式值)
# v1.1 新代码:
r = ToolResult(tool_call_id="x", content="blocked",
               execution_status="block_l1", denied_by="l1_blacklist")
#  → is_error=True(派生);无需显式传 is_error
```

下游代码(`conversation.add_tool_result()` / `TUI tool_card.py` / LLM 喂回消息)
**只读 is_error 仍正确**;新代码建议优先读 `execution_status` 拿全信息
(LLM 反馈文案、TUI 区分色块用)。

## 六、配置新增块

```yaml
# config.yaml v1.1 新增块(可省略,整块省 → v1.0 等价行为)
hooks:
  - id: <unique>
    event: <11 values>
    if: {all: [...]}  # 或 {any: [...]};可省
    actions:
      - action: shell|http|prompt|sub-agent
        # 子字段见 §4
    async: true        # 仅 tool.post 允许
    timeout_seconds: 30
    run_once: false
```

### 校验失败处理

启动期 `HookRegistry.freeze()` 一次跑完所有校验,任何错误 → `SystemExit(1)`。
错误聚合打印(不全跳出在第一个):

```
ERROR: hooks validation failed (N error(s)):
  - hooks[bad]: empty actions list
  - hooks[bad-async]: async not allowed for tool.pre events
  - hooks[no-stable-on-tool]: slot=stable_system not allowed for tool.* events
  - hooks[both-all-any]: `if.all` and `if.any` are mutually exclusive
```

**临时绕过**:把 `hooks:` 块整段注释掉 / 删除 → 重启 → v1.0 行为恢复
(legacy `_v5_executor` 路径,跟 v1.0 byte-identical)。

## 七、最少动作升级

1. **什么都不改直接升级**:`pip install baozicode==1.1.0`,配置 / 命令 / Skill
   行为完全保留。`Agent` 不收 `hook_registry` 时走 legacy `_v5_executor`(等同 v1.0)
2. **第一个 hook**:复制 `config.example.yaml` 的 `audit-bash-pre` 块到你的
   `config.yaml` 顶部 `hooks:` 下,改 `command` 指向你的审计文件路径,重启
3. **加 sticky reminder**:写一个 `event: turn.start` + `action: prompt` +
   `slot: sticky_reminder`,每轮起头把项目约定塞进 LLM 视野
4. **完整审计**:`event: tool.post` + `async: true` + `action: shell` 把所有
   bash 调用落 `.baozicode/audit.log`,不阻塞主流程
5. **禁用 hooks**:整段删 `config.yaml` 的 `hooks:` 块 → 重启 → v1.0 行为完全恢复

## 八、迁移常见问题

**Q: hooks 跟 v0.5 权限规则什么关系?能互相替代吗?**  
A: 不能完全替代。L1 硬黑名单(`rm -rf` / `sudo` / `chmod 777` 等)永远 hard-wall,
hook.allow 也绕不过。L2-L5 是配置型策略(`Bash(git *)` 之类),适合「一类调用通用规则」;
hook 适合「带运行时参数决策」(`if: arg.command: regex "..."`)或「非权限语义」
(写日志 / 注入提醒 / 发 HTTP 风控)。两者互补。

**Q: hook.pre 拒的工具调用,LLM 看到的是什么?**  
A: `ToolResult` 喂回 LLM,字段:
```
content: "<hook stdout 第一行,或 hook_result.reason>"
execution_status: block_hook_pre
denied_by: hook_pre
denied_hook_id: <hook.id>
is_error: True(派生)
```
LLM 据此调整策略(下一轮通常会换工具 / 换参数 / 改路径)。

**Q: hook 抛异常 / 超时了,Agent 会怎样?**  
A: 仅 `log.warning`,Agent 主流程**不阻断**(fail-open)。与权限系统的
fail-closed 形成对称 — hook 是用户扩展,代码质量不可控,绝不能让无关 hook
阻塞核心任务。配置错的 hook 启动期就 SystemExit(校验早暴露)。

**Q: async post 跟 sync post 的差别?**  
A: `async: true` 让 shell/http/sub-agent 走 `asyncio.create_task`,
不阻塞下一轮;默认 (`enqueue: false`) 只写日志,stdout 不进 LLM 上下文。
配 `enqueue: true` 时,hook 跑完调 `Agent.enqueue_reminder(kind="hook_prompt",
body=stdout, ttl="once")`,下一轮 `messages[-2]` 注入 `<system-reminder
type="hook_prompt">`。

**Q: 多个 hook 同一事件同时触发,执行顺序?**  
A: YAML 数组顺序执行(`config.yaml` 声明顺序)。**串行短路**:
首个 deny 赢,后续 hook 不跑。`tool.pre` 同步执行;`tool.post` 默认同步,
`async: true` 才后台化(只对 post 允许,pre 不允许)。

**Q: hook.pre 拦截能由用户在 Modal 里覆盖吗?**  
A: 不能。hook.pre 的 deny 跟 L1 一样是硬决策,不让用户在 L5 Modal 里覆盖
(否则 hook.allow 也可能被用户覆盖,hook 安全基线被削弱)。要绕过改 hook
配置,临时禁用对应 hook 后重启。

**Q: `parse_expr` 的 sandbox 安全吗?**  
A: 用 `simpleeval`(无 exec / 无 import / 无 lambda / 无函数调用),只能读
`res` / `body` / `status` / `headers` 标识符 + 字面量比较 + 属性赋值。
不会 RCE。v1.2 评估替换为 `asteval`(支持更复杂表达式)做更严的沙箱;
v1.1 simpleeval 已能覆盖 95% 用例。

**Q: 我能在 `tool.post` 里用 `slot: stable_system` 吗?**  
A: 不能(配置校验拒绝,`SystemExit`)。
`tool.post` 在 LLM stream 之后才触发,此时 `BuiltPrompt.stable_system`
已经为下一轮准备好了,中途变更会破坏缓存 byte-identical。`stable_system`
只能配在 `session.*` / `turn.*` / `message.*` / `system.*` 事件。

**Q: 怎么写测试覆盖我的 hook?**  
A: `tests/test_hooks_v11.py` 是参考样例。关键测试点:
- schema — `parse_hook_def({"id":..., "event":..., "actions":[...]})` 成功解析
- condition — 4 种匹配 + all/any + not_ 前缀各跑 1 个 case
- executor — shell success / shell nonzero deny / prompt enqueue 调
  `agent.enqueue_reminder`
- dispatcher — 多 hook 串行短路 + condition 不命中跳过 + hook 异常 fail-open
- Agent pipeline — 无 hook 时 byte-identical 等价 v1.0;有 hook 时
  `ToolResult.execution_status` 填对
- registry.freeze() — 故意配坏,断言 `HookValidationError` 聚合多个错

**Q: hooks 的审计日志存在哪里?**  
A: 默认 `<project>/.baozicode/hooks/<session>.audit.jsonl`,
每行一条 `HookInvocation` 记录(包含 `ts` / `hook_id` / `event` /
`tool_name` / `tool_call_id` / `action_results` / `duration_ms` /
`outcome: allowed|denied|error`)。启动期按 100 MB 轮转到
`*.audit.jsonl.YYYYMMDD-HHMMSS`。TUI 现在不显示这个文件(避免污染
工具结果卡),用 `cat` / `jq` 直接看即可。

**Q: 不写 `hooks:` 块跟 v1.0 完全等价吗?**  
A: 是。`AppConfig.hooks is None` → `BaoZiCodeApp.__init__` 直接跳过整层,
`Agent` 不收 `hook_registry`,走 legacy `_v5_executor`(L1 → L2 → L3 → L4 → L5
→ execute),与 v1.0 byte-identical。

**Q: 调 `load_skill` 时 hook 会拦吗?**  
A: 会。`load_skill` 是 system 工具(`tool_type="internal"`),但 hook 是基于
事件 + 工具参数条件的,不区分系统 / 用户工具 — `event: tool.pre` 一样会拦。
若不希望 hook 影响 skill 加载,在条件里加白名单:

```yaml
- event: tool.pre
  if:
    any:
      - tool: "Bash"
      - tool: "Read"
      - tool: "Write"
      - tool: "Edit"
  # (不写 load_skill)
  actions:
    - action: shell
      command: "..."
```
