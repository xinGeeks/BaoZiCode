# v1.1 → v1.2 迁移指南

v1.2 是 v1.1 之后的**小步 polish**:把 v1.1 承诺但没接通的 4 个 hooks 收尾点落地。
**无 breaking change** — 不写 `hooks:` 块的 v1.0/v1.1 项目行为完全保留;
写了 `hooks:` 块但没碰新字段的项目,行为也保留。

---

## 一、发生了什么变化

| 维度 | v1.1 | v1.2 |
|------|------|------|
| `system.compaction` 事件 | spec 写"reserved",Agent.run 偶发 fire,`maybe_compact` 入口**不 fire** | `maybe_compact(...)` 入口**必 fire**(若有 hook dispatcher);payload `{trigger, tokens_before}` |
| `system.cancel` 事件 | fire 时 payload 是字符串 `"user_interrupt"` | payload 改 dict `{reason: "user_cancelled", iteration: int}`(可能影响 v1.1 hook 写法) |
| Action kind | 4 种:`shell` / `http` / `prompt` / `sub-agent` | +2 种 control action:`clear_sticky_reminders` / `clear_stable_system_overrides` |
| TUI ToolResultCard 颜色 | 单一色(无 execution_status 区分) | 5 种 `execution_status` 各一色(红/黄/橙/绿/红);`None` 走默认(向后兼容) |
| `Agent._pending_reminders` / `_hook_stable_overrides` | 只能由 hook `prompt` 注入累积,无显式清空 | 配套 2 个 control action 显式清;`_temp_reminders` 仍由 `_inject_reminders` 自动消费 |

---

## 二、新 Action Kind — control action

v1.2 加 2 个 **control action**,语义独立 — 各自只清 Agent 上的一类 hook 注入状态。
它们**没有拒绝能力**,也不能配 `parse_expr` / `deny` / `deny_reason`(Pydantic
`extra="forbid"` 启动期就拦)。

### 2.1 总表

| Action kind | 清的状态 | **不动**的状态 | 字段 |
|---|---|---|---|
| `clear_sticky_reminders` | `Agent._pending_reminders` | `_hook_stable_overrides` / `_temp_reminders` | (无) |
| `clear_stable_system_overrides` | `Agent._hook_stable_overrides` | `_pending_reminders` / `_temp_reminders` | (无) |

> **`_temp_reminders` 不在 clear 范围**:本意是 turn-scoped,下轮 `_inject_reminders`
> 消费即自动清,无需显式 clear action。

### 2.2 用法示例

```yaml
hooks:
  # ① turn.start 时清空旧的 sticky reminder,防止累积
  - id: reset-sticky-each-turn
    event: turn.start
    actions:
      - action: clear_sticky_reminders

  # ② tool.post 命中特定 deny 时,清掉之前 hook 注入到 stable_system 的临时 override
  - id: clear-overrides-on-block
    event: tool.post
    if:
      all:
        - tool: "Bash"
    actions:
      - action: clear_stable_system_overrides
```

### 2.3 返回值

`ActionResult(deny=False, ...)` — 永不 deny(control action,语义只清状态)。

### 2.4 与 v1.1 `clear_hook_runtime_state` helper 的关系

`baozicode.hooks.clear_hook_runtime_state(agent)` 是 v1.1.1 引入的 **三合一 helper**
(同时清 3 类状态)。v1.2 的 2 个 control action 是**更细粒度**版本,允许用户在
不同 event 下分别精确清一类。如果你的项目之前用 `clear_hook_runtime_state`,
且要保留"3 类全清"语义,在 hook action 里调这个 helper 即可(用 `shell` action
跑 `python -c "from baozicode.hooks import clear_hook_runtime_state; ..."`
不优雅 — 推荐改用 v1.2 的 2 个 control action 串行)。

## 三、System 事件 payload 微调

### 3.1 `system.compaction` — payload 从缺位到齐

| 版本 | 何时 fire | payload |
|---|---|---|
| v1.0 / v1.1 | Agent.run 手动路径偶发 fire | 字符串 `"manual"` |
| **v1.2** | `maybe_compact(...)` 入口**每次必 fire**(`hook_dispatcher is not None` 时) | dict `{"trigger": "auto" \| "manual", "tokens_before": int}` |

**实际效果**:v1.1 spec 写"reserved"但 `maybe_compact` 不 fire,导致用户无法 hook
压缩前/后的时机。v1.2 把 `maybe_compact` 入口接通,**手动和自动触发都会 fire**。

**用法示例**:

```yaml
hooks:
  # 压缩前先写一行"压缩前快照"到本地日志
  - id: log-pre-compaction
    event: system.compaction
    actions:
      - action: shell
        command: |
          echo "[$(date -Iseconds)] compaction trigger=$EVENT_ARG_0 tokens_before=$EVENT_ARG_1" \
            >> ~/.config/baozicode/compaction.log
```

> `trigger` 和 `tokens_before` 通过 env var 暴露 — **位置**用
> `$EVENT_ARG_0` / `$EVENT_ARG_1`(`trigger` 在前,`tokens_before` 在后);
> **命名键**用 `$EVENT_TRIGGER` / `$EVENT_TOKENS_BEFORE`(大写)。
> tool.pre / tool.post 仍走 `$ARG_<NAME>`(ToolCall.arguments 路径,v1.1 行为不变)。

### 3.2 `system.cancel` — payload 字符串 → dict

| 版本 | payload |
|---|---|
| v1.0 / v1.1 | 字符串 `"user_interrupt"` |
| **v1.2** | dict `{"reason": "user_cancelled", "iteration": int}` |

**潜在 breaking**(v1.2 唯一的格式变化):如果你在 v1.1.1 hook YAML 里用
`event: system.cancel` 写 `parse_expr` 且依赖 payload 是字符串,需要改成读 dict:

```yaml
# v1.1.1 写法(payload 是 str,parse_expr 比对字符串)
- id: cancel-old
  event: system.cancel
  actions:
    - action: http
      url: http://audit.example/cancel
      method: POST
      parse_expr: 'res.deny = res.status == 500'   # ❌ v1.2 payload 不是 str

# v1.2 写法(payload 是 dict)
- id: cancel-new
  event: system.cancel
  actions:
    - action: http
      url: http://audit.example/cancel
      method: POST
      body:
        reason: "$EVENT_ARG_0"        # v1.2 把 payload 字段按 key 暴露成 EVENT_ARG_<i>
        iteration: "$EVENT_ARG_1"
      parse_expr: 'res.deny = res.status == 500'
```

> **不写 system.cancel hook 的项目零影响** — 这是 v1.1.1 → v1.2 唯一会触达的
> 行为差异。如果你不确定项目里有没有这个 hook,跑 `grep -r "system.cancel" config*.yaml` 看一下。

## 四、TUI ToolResultCard 颜色

v1.2 起,`ToolResultCard` 按 `execution_status` 上色:

| execution_status | 颜色 | 含义 |
|---|---|---|
| `block_l1` | 红(`$error`) | L1 黑名单硬拦截 |
| `block_hook_pre` | 黄(`$warning`) | hook.pre 拒 |
| `block_permission` | 橙(`#ffa500`) | L2-L5 拒 |
| `executed_success` | 绿(`$success`) | 工具成功 |
| `executed_failed` | 红(`$error`) | 工具自身抛错 |
| `None` | 默认 | v1.0/v1.1 旧 ToolResult,无 `execution_status` 字段 |

**视觉上**:TUI 一眼区分 5 种结局;旧 ToolResult 走默认色,零影响。

> 颜色具体值在 `baozicode/tui/styles.tcss` 的 `ToolResultCard.-block-l1` 等规则里;
> 想换主题改 `styles.tcss` 即可,不需要动 Python。

---

## 五、零影响 / 无需迁移

- **不写 `hooks:` 块的项目** — v1.0 → v1.2 行为完全一致,跳过本指南
- **写了 `hooks:` 块但没碰 system.cancel 的项目** — 零影响
- **Agent / ToolResult 已有字段未变** — `execution_status` / `denied_by` / `denied_hook_id` 都在 v1.1 加过,v1.2 不改
- **5 防御权限 (L1-L5)** — 未动
- **上下文压缩 (Layer 1/2)** — 行为不变,只是多了 1 个 hook fire
- **所有非 hook 子系统**(skills / commands / memory / sessions / instructions / mcp)— 未动

---

## 六、最少动作升级

1. 升 `baozicode` 到 v1.2
2. 跑 `grep -r "system.cancel" config*.yaml`:如果有,改 payload 用法(见 §3.2)
3. (可选)在 `config.yaml` 加 1-2 个 v1.2 control action,体验新能力
4. 重启 → TUI 立刻看到 ToolResultCard 5 色

## 七、常见问题

**Q: v1.1 写的 `event: system.compaction` hook 在 v1.2 行为变了吗?**
A: 行为更稳定 — v1.1 `maybe_compact` 不 fire,只有 Agent 手动路径偶发 fire;v1.2
每次 `maybe_compact(...)` 入口都 fire(无论手动 / 自动)。如果你只想接"自动压缩",
用 `if: arg.trigger == "auto"` 过滤(注:v1.2 通过 env var `$EVENT_ARG_0` 暴露
trigger 字符串)。

**Q: clear_sticky_reminders 和 v1.1.1 `clear_hook_runtime_state` 哪个用?**
A: 看场景。需要精确控制(只清一类)→ v1.2 的 2 个 control action;需要"3 类都清"
→ 继续用 v1.1.1 helper(在 shell action 里调 Python API 不优雅,建议改成
v1.2 的 2 个 action 串行 — 等价效果)。

**Q: TUI 颜色能改吗?**
A: 能。改 `baozicode/tui/styles.tcss` 的 `ToolResultCard.-block-l1` 等 5 条
规则里的 `color` / `border-left` 即可。Textual CSS 语法,详见 Textual 文档。

**Q: clear action 的 deny 默认是 False,能强制 deny 吗?**
A: 不能,这是 control action 的本质(Pydantic 拒绝 `deny` 字段,
`extra="forbid"`)。需要 deny 能力用 `shell` / `http` / `sub-agent`。

**Q: 我没装 `hooks:` 块,v1.2 还会多 fire system.compaction / system.cancel 吗?**
A: 不会。`hook_dispatcher is None` 时 fire 整块跳过,性能零损耗。
