# v1.4 Foundation → v1.4 Tools 迁移指南

v1.4 是分 4 个独立 proposal 推进的大版本。本文档覆盖第 2 个
proposal —— **`v1-4-team-tools`** —— 在 v1-4-team-foundation 之上加
**6 个 Lead-only 协作工具 + 共享任务清单 + Approval 协议 + MailboxNotifier +
角色过滤**。

Foundation 已铺好的层(schema / mailbox / lockfile / CLI / 持久化目录)
在 tools 阶段**不变**;tools 阶段**只**在这层之上加 first-class 工具 + 角色
语义 + 自动 state 转换。team pane 实际派生 / coordinator 模式留给后续 2 个
proposal(`v1-4-team-pane-backend` / `v1-4-team-coordinator`)。

## 无 breaking change

升级 v1.4 tools 后:

- 主对话照常跑(默认 `role='subagent'`,拿不到任何 team_* 工具,行为等同 v1.3)
- v1.4 Foundation 的 `baozicode team <action>` CLI 子命令 + `teams:` 配置
  块都不动
- `ToolDefinition` 新字段 `role_visibility` 默认 `None`,老工具 zero 修改
- `ToolRegistry.get_all_tools(role=None)` 默认参数,v1.3 12 个调用点零修改
- `Agent` 新增 keyword-only 参数 `role` 默认 `'subagent'`,老 Agent 构造零修改
- 仅当 `App.active_team_name` 非空(由 `baozicode team use <name>` 或
  TUI `/session use` 触发)时,ChatScreen 重建 Agent 才升级为
  `role='lead'` + 拿到 13 工具(7 内置 + 6 team_*)

## Lead 角色切换

激活 team 后,Lead Agent 实例会**升级** ——不是普通主 Agent。

```bash
# Foundation CLI 已建 team
baozicode team create devops
baozicode team show devops

# 激活 —— 用后 ChatScreen 重建 Agent 时 role='lead'
baozicode team use devops

# 或在 TUI 内调 /session use devops(等价)
```

激活后的行为变化:

- Agent 角色由 `subagent` 升到 `lead`,自动看到 6 个 team_* 工具
- 每轮 `Agent._inject_reminders` 跑 `MailboxNotifier.build_reminder()`
  扫所有 member outbox,把新消息(PLAN / TASK-COMPLETE / TASK-FAILED /
  普通消息)拼成 `<system-reminder type="team_mailbox">` 塞到 Lead
  conversation
- 6 个 team_* 工具全部 `side_effect=True`、`risk="low"`、`role_visibility=
  ['lead']`,经 v0.5 五层防御后**强制必填** `team` + `member` 参数

## 6 个 Lead-only 协作工具

| 工具               | 参数                                                | 副作用                                                                                              |
|--------------------|-----------------------------------------------------|-----------------------------------------------------------------------------------------------------|
| `team_dispatch`    | `team`, `member`, `task_id?`, `body?`               | 写 inbox + `touch_wake` + 若 `task_id` 非空自动 `Tasks.update_status(in_progress, assignee)`       |
| `team_send_message`| `team`, `member`, `body`                            | 写 inbox + `touch_wake`;body 含 `APPROVED: <id>` / `REJECTED: <id>` 触发审批语义                     |
| `team_cancel`      | `team`, `member`, `reason?`, `terminate=false`      | `terminate=False` 写 `CANCEL: <reason>` + 当前 task → `canceled`;`terminate=true` 改 state offline + `os.kill(state.backend_pid, SIGTERM)` |
| `team_merge`       | `team`, `target='main'`, `dry_run=false`            | 字典序 `git merge --no-ff wt/<member>` 顺序合到 target;冲突 `git merge --abort` + 返 aborted 列表 |
| `team_task_create` | `team`, `body`, `depends_on=[]`, `auto_ready=true` | 8 字符 hex id(`secrets.token_hex(4)`)+ cycle 检测 + 自动 status `ready` / `pending`                |
| `team_task_query`  | `team`, `status_filter=[]`, `assignee=None`, `include_ready_graph=false` | 按 status / assignee 过滤 + 可选 `ready_for_dispatch` 布尔                                       |

返回全是 `ToolResult.success("", text)`,错误用 `ToolResult.error_result
("", reason)`,executor 不抛异常上 Agent 主循环。

## 共享任务清单

`<teams_dir>/<team>/tasks.jsonl` —— JSONL append(同 id 单条,`Tasks.update_status`
是 read-modify-replace 整文件 write-then-rename):

```
{"id":"3f4a7c01","body":"改 api/users.py","status":"pending","depends_on":[],"assignee":null,"created_at":"...","started_at":null,"completed_at":null,"error":null}
{"id":"a1b2c3d4","body":"改 tests/","status":"pending","depends_on":["3f4a7c01"],...}
{"id":"5e6f7080","body":"改 docs/","status":"ready","depends_on":["3f4a7c01"],...}
```

6 状态字面量(契约见 `specs/team-management/spec.md::Task`):

| 状态           | 含义                                              |
|----------------|---------------------------------------------------|
| `pending`      | 已创建,deps 未满足                                |
| `ready`        | deps 全部 `done` / `canceled`(自动 transition)    |
| `in_progress`  | 已被某 member 接管                                |
| `done`         | 成功(member 写 `---TASK-COMPLETE-<id>---` 触发)  |
| `failed`       | 失败(member 写 `---TASK-FAILED-<id>---` 触发)     |
| `canceled`     | Lead 显式取消                                    |

`Tasks.find_ready` 拓扑门控 —— 所有 deps ∈ {`done`, `canceled`} 才返 ready;
失败 dep 当 blocker(不视作 passed)。`Tasks.detect_cycles` DFS 检测
self / 2-ary / 3-ary cycle,`TaskCycleError` 在 `team_task_create` 拒绝写入。

## Approval 协议(走 mailbox 文本)

不走新文件、不走新锁、不走新协议层 — 复用 Foundation 的 `Mailbox`。

```
member outbox      ---PLAN-3f4a7c---
                   我会先改 X 然后补 Y
                   ---END---

                             ↓ MailboxNotifier 扫
Lead sys-reminder alice (waiting) submitted plan 3f4a7c:
                     我会先改 X 然后补 Y
                     回复: APPROVED: 3f4a7c 或 REJECTED: 3f4a7c <reason>

                             ↓ Lead LLM 看后决定
Lead inbox         APPROVED: 3f4a7c
或                 REJECTED: 3f4a7c 不要改 X
                             ↓
                   member loop 醒来看 inbox 匹配 plan_id
```

`ApprovalProtocol` 5 个静态方法(`baozicode/teams/approval.py`):
`parse_plan` / `parse_approval` / `send_approval`(封装
`Mailbox.append_message + Mailbox.touch_wake`)/ `is_task_complete` /
`is_task_failed`。`REJECTED` 强制要求非空 `reason`。

## MailboxNotifier

Lead Agent 每轮 LLM 决策前自动触发(`Agent._inject_reminders` 内置 hook,
只在 `role='lead'` 生效):

1. 扫 `<teams_dir>/<team>/<member>/outbox.jsonl`
2. 与 `_seen_hashes: set[str]`(跨 `Agent.run` 持久)做 dedup
3. 分类新消息:
   - `TASK-COMPLETE-<id>` → 自动 `Tasks.update_status(done)` +
     `Mailbox.write_state(idle)` + reminder 注入 summary
   - `TASK-FAILED-<id>` → 同上 + `error` 字段
   - `PLAN-<id>` → 注入 reminder 等 Lead approve / reject
   - 普通消息 → 截 200 字注入 reminder
4. 拼 `<system-reminder type="team_mailbox">` 块塞到 Lead conversation
   `messages[-2]`,Lead LLM 决策后即可丢弃(永久内容仍由 member outbox
   文件承担)

容错:notifier 抛异常 → Agent 不挂,`log warning` 继续,完成度照常。

## 角色过滤

3 处改动:

| 位置                                  | 变更                                                                                              |
|---------------------------------------|---------------------------------------------------------------------------------------------------|
| `baozicode/tools/base.py`             | `ToolDefinition.role_visibility: list[str] \| None`,`__post_init__` 校验 ∈ `AGENT_ROLES = frozenset({'lead','member','subagent','coordinator'})` |
| `baozicode/tools/registry.py`         | `ToolRegistry.get_all_tools(role: str \| None = None)`:`role=None` 老路径返全部;非空按 role 过滤    |
| `baozicode/agent/loop.py`             | `Agent.__init__` 新增 `role: Literal = 'subagent'` keyword-only + `Agent.role` property;`Agent._filter_tools_by_role` 优先用 `tool_registry.get_all_tools(role=...)`,否则就地过滤 |

7 个内置工具(`Read` / `Write` / `Edit` / `Bash` / `Grep` / `Glob` /
`WebFetch`)全部保持 `role_visibility=None` —— 向后兼容 v1.3。
6 个 team_* 工具全部 `role_visibility=['lead']`。

注意:`role='member'` / `'subagent'` / `'coordinator'` 都接受
(`coordinator` 是为 v1-4-team-coordinator 占位),但当前**没有任何**
`role_visibility=['coordinator']` 的工具,直到 coordinator proposal 引入
白名单收缩。`tool_type='internal'` 工具(如 `load_skill`)不受 role
过滤影响 —— 默认全员可见。

## 没做什么(留给后续 proposal)

- `team_cancel(terminate=True)` 调 `os.kill(state.backend_pid, SIGTERM)` 是
  **占位** —— pane-backend 没注入前 `state.backend_pid=None`,静默 no-op;
  tmux / iTerm2 / Windows Terminal pane 派生由
  `v1-4-team-pane-backend` 填充 → 见 `MailboxNotFound.on_unmount` 注释
- Lead 主动剥夺写工具的 coordinator 模式(配置 + env var 双锁)由
  `v1-4-team-coordinator` 填充
- 跨机器分布式团队、成员间实时流式通信、复杂任务依赖约束 —— **永远不做**
  (v1.4 scope 外)

## FAQ

**Q: Lead 不激活 team 时是 subagent 吗?lead 怎么激活?**

A: `App.active_team_name=None` 时 `ChatScreen` 切回 `role='subagent'`,
   拿到 7 个内置工具,看不到 team_*(等同 v1.3 主对话)。
   激活走 `baozicode team use <name>`(CLI)或 TUI `/session use <name>`。

**Q: 6 个 team_* 工具权限怎么走?也要过五层防御吗?**

A: 是。`team_*` 全部 `side_effect=True`、`risk="low"`,走 v0.5 五层防御
   (L1 黑名单 / L2 sandbox / L3 rule / L4 mode / L5 Modal)。Lead role
   不绕过权限,只是让 Lead 看到这些工具 + 工具在权限上不被默认 deny。

**Q: 任务执行出错(mid-task panic)tasks.jsonl 状态怎么修?**

A: 中途 agent 死 / 用户 Ctrl-C / pane 崩,lead LLM 下次重新读
   `team_task_query(status_filter=["in_progress"])` 找挂着的任务,
   用 `team_cancel` 标 canceled 或重新 `team_dispatch` 接续。

**Q: 我能不激活 team,只用 task 工具吗?**

A: 可以。`task` 是 SubAgent 委派的 v1.2 工具(独立模块,不含 team_*)。
   team_* 必须有 active_team_name 才能让 Lead 看到。本提案
   6 个工具完全独立,可以只跑 `team_task_*` 不用 member(当作
   任务管理数据库用)。

**Q: 任务依赖深度可以多少?**

A: 提案只保证 6 状态字面量 + 简单 `depends_on: list[str]` 拓扑门控;
   `Tasks.find_ready` N² 扫(<20 任务够用)。
   复杂任务依赖约束(条件触发 / 资源约束 / 优先级)是 v1.4 范围外,
   不引入 Kahn 等复杂算法。

**Q: completion 报告能含更多 detail 吗?**

A: 可以。`---TASK-COMPLETE-<id>--- ... ---END---` 中间 body 任意
   plain text —— LLM 自动看到摘要由 `MailboxNotifier` 转 reminder。
   summary 由 LLM 在 Member 端写入,Lead 不解析。

**Q: 成员可不可以直接给 Lead 发消息(Member → Lead)然后 Lead 必须回?**

A: 可以(`ApprovalProtocol.parse_plan` 等都已就绪),但 Lead 是否回
   是 LLM 决策 —— 默认 Lead Agent 看 reminder 决定要不要
   `team_send_message` 回,不会强阻塞。R3 风险:
   Approval 死锁由 Lead 5 分钟无活动 → 自动 `team_cancel` 缓解。
