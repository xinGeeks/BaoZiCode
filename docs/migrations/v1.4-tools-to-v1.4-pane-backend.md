# v1.4 Tools → v1.4 Pane Backend 迁移指南

v1.4 是分 4 个独立 proposal 推进的大版本。本文档覆盖第 3 个
proposal —— **`v1-4-team-pane-backend`** —— 在 v1-4-team-foundation +
v1-4-team-tools 之上落地 **member pane 实际派生 + wake 唤醒 +
state.json resume + 5 BackendType 实现 + BackendManager 居中调度**。

foundation 已铺好的层(schema / mailbox / lockfile / CLI / 持久化目录)
和 tools 阶段的 6 个 Lead-only 工具 + 共享任务清单 + Approval 协议
**不变**;pane-backend 只在这层之上加派生 / 唤醒 / resume 路径。
coordinator 模式留给后续 proposal(`v1-4-team-coordinator`)。

## 无 breaking change

升级 v1.4 pane-backend 后:

- 主对话照常跑(默认 `role='subagent'`,行为等同 v1.3)
- v1.4 foundation / tools 的 `baozicode team <action>` + `baozicode member run` +
  6 个 team_* 工具 + `teams:` 配置块都不动
- `ToolDefinition.role_visibility` 字段语义不变
- `Agent` keyword-only 参数 `role` 默认 `'subagent'` 不变
- `register_team_tools` 新增 keyword-only `backend_manager=None` 参数,
  老调用点零修改;`backend_manager=None` 时 `team_dispatch` /
  `team_cancel` 走 v1-4-team-tools 阶段行为(无 spawn / 裸 os.kill)
- 仅当 `BaoZiCodeApp._build_teams_registry` 跑过(`teams.enabled=True`)
  时,`self.backend_manager` 自动构造 singleton;teams disabled → None

## BackendType 选型

`Member.backend` 字段(v1.4 schema)扩展到 5 个字面量,默认 `coroutine`:

| BackendType           | 平台       | 启动方式                              | pane 句柄                  |
|-----------------------|------------|---------------------------------------|----------------------------|
| `pane-tmux`           | Linux/macOS| `tmux split-window -t <session>`      | `pane_id` (`%N`)           |
| `pane-iterm2`         | macOS      | AppleScript 新 tab                    | `window_id`                |
| `pane-windows-terminal` | Windows  | `wt.exe -w 0 nt`                       | `tab_uuid`                 |
| `coroutine`           | 全部       | 进程内 `asyncio.Task`                 | 无                         |
| `worktree-coroutine`  | 全部       | coroutine + v1.3 WorktreeManager      | 无                         |

`BackendManager.effective_backend(member)` 决策:

1. 显式 `member.backend in {pane-tmux, pane-iterm2, pane-windows-terminal}`
   → 强用(healthy 才 spawn,否则降级 `coroutine` + log warn)
2. 显式 `member.backend == "worktree-coroutine"` → 保留
3. `member.backend == "coroutine"` 且 pane 健康 → 按 sys.platform 升级:
   Windows → pane-windows-terminal / macOS → pane-iterm2 /
   Linux → pane-tmux
4. pane 全部不可用 → 仍 `coroutine`

## CLI 调用流程

```bash
# Lead Agent 通过 team_dispatch 派生 member 后,
# 后台 pane / coroutine 进程跑:
baozicode member run --team devops --name alice

# 等价后台启动(Linux + tmux):
baozicode member run --team devops --name alice --cwd /tmp/alice-wt
```

CLI 内部流程:

1. `TeamsRegistry.bootstrap(config)`(team 不存在 → exit 3)
2. `team = store.show()` + `member = team.members[name]`(不存在 → exit 6)
3. `os.chdir(args.cwd or member.workdir)`(不存在则 mkdir)
4. `load_config(...)` + `create_client(config)` + `permissions.bootstrap(...)`
5. `loop = MemberMainLoop(registry, team, member, llm_client, config, permissions, cwd)`
6. 注册 SIGINT/SIGTERM handler(Unix `loop.add_signal_handler` /
   Windows `signal.signal` fallback)
7. `await loop.run()`(graceful exit 后 state=offline)

退出码:

- `0` — graceful(LLM 完成 / SIGINT/SIGTERM)
- `3` — team 不存在(`TeamNotFound`)
- `6` — member 不存在(`MemberNotFound`)
- `4` — IO / 权限错(`OSError` / `PermissionError`)
- `5` — 配置错误(`ConfigError`)
- `2` — argparse(`--team` / `--name` 缺)

## Member lifecycle

```
Lead 调 team_dispatch(team, member, body, task_id?)
  ↓
  Mailbox.append_message(inbox) + Mailbox.touch_wake
  ↓ (BackendManager.spawn_if_offline)
  effective_backend → 选 pane / coroutine
  ↓
  handle.spawn() → pane 起 / asyncio.Task 起
  ↓
  Mailbox.write_state(idle + backend_pid)
  ↓
  PaneInfo.save(pane_identifier + pid + last_active_ts)
  ↓
Member MainLoop 轮询 wait_for_wake(200ms):
  → wake.signal mtime 变化 → _run_turn(fresh Agent)
    → AgentEvent(text / tool_call / tool_result / done)
    → tool 发出 mailbox write → outbox.append_message
    → DONE → state=idle + 继续等
  → loop.request_terminate() (SIGINT / SIGTERM) → state=offline
```

跨 Lead restart 时 `BackendManager.restore_panes(team)`:

- 读 `<teams_dir>/<team>/pane_info.json`
- 每 member 调 `os.kill(pid, 0)` 验证还活
- 活 → `_RestoredHandle`(只 is_alive / kill,不能 title / spawn)
- 死 → 移除 entry + log info
